# Python 后端架构

当前项目只有 `app/__init__.py` 和 `app/main.py` 两个 Python 源文件，入口提供 `GET /api/v1/health`。下文记录企业安全生产管理系统的后续设计，业务目录和技术组件会在对应阶段加入。

## 目标与决策

首要目标是通过重新实现企业安全生产管理系统，学习 Python 后端开发。现有 Java 系统提供业务参考，Python 实现允许重新组织代码与表结构。

前端独立开发，通过 HTTP JSON API 与后端交互，需要实时数据时增加 WebSocket。前后端由同一开发者维护，接口仍应明确参数、返回值和错误语义。

后端采用模块化单体：一个应用包含多个业务模块，作为一个版本构建与发布，可按需要运行多个应用实例。后台任务执行器未来可单独运行，仍复用同一项目的业务代码。初期不引入微服务网关、注册中心和跨服务事务。

当前使用 FastAPI、Uvicorn 和 uv，Python 开发版本固定为 3.13.16，依赖版本记录在 `uv.lock`。学习请求和响应模型时使用 Pydantic，数据库阶段再引入 SQLAlchemy、Alembic 和 MySQL。初期优先使用同步数据库访问与同步业务函数，先掌握会话和事务，再根据外部网络调用等需求引入异步。

## 规划中的整体结构

```text
独立前端
   │ HTTP JSON / 后续 WebSocket
   ▼
FastAPI 应用
   ├─ 接口层：路由、参数校验、身份获取
   ├─ 业务模块：业务规则、权限范围、事务、模块协作
   ├─ 数据访问：SQLAlchemy 模型与查询
   └─ 外部适配：文件存储、第三方平台、设备协议
          │
          ▼
        MySQL

后续按需求加入 Redis、消息队列、任务执行器和实时广播。
```

HTTP 入口统一使用 `/api/v1` 前缀，例如 `/api/v1/foundation/positions`。接口文档供前后端联调使用；HTTP 状态码表达请求结果，响应结构和分页格式在第一个接口实现时统一确定。

## 业务模块边界

下表是基于原项目扫描结果确定的第一版归属。旧系统的具体表和字段迁移到对应模块前，仍需核对实际代码与业务使用情况。

| Python 模块 | 主要职责与数据归属 | 原 Java 业务参考 |
|---|---|---|
| system | 用户、部门组织、角色、菜单与操作权限、字典、操作审计；用户与企业的归属关系 | fan-auth |
| foundation | 企业业务档案、岗位、生产线、设备基础台账、化学品、资质、承包商 | fan-foundation |
| risk | 风险辨识与分级、管控措施、巡检计划与任务、隐患和整改闭环 | fan-currency |
| hazard | 重大危险源档案、监测指标配置、监测记录和预警业务 | fan-hazard，以及基础模块中重叠的危险源业务 |
| work | 作业计划、作业票、参与人员、安全措施、检测记录与作业状态 | fan-work |
| education | 培训计划、课程、题目、学习记录、考试和学时 | fan-education |
| emergency | 预案、处置卡、应急物资与队伍、演练、事故案例 | fan-emergency |
| standard | 标准化目标、制度、考评、整改与持续改进；引用其他模块已有台账 | fan-standard |
| checklist | 责任、岗位操作、巡检等清单模板与条目；具体执行记录由执行业务管理 | fan-inventory |
| storage | 仓库、库存、出入库、产品流向与仓储业务记录 | fan-storage |
| gate | 预约、车辆、出入授权、黑白名单、区域和通行记录 | fan-gate 与 fan-gate-v8 |
| workflow | 流程定义与版本、节点、审批任务、通用表单定义、审批历史 | fan-process-engine 与公共模块的审批逻辑 |
| mapping | 图层、标绘、图标与空间对象；业务对象仍归属各业务模块 | fan-plotting |
| dashboard | 跨模块统计查询与大屏聚合，不修改业务源数据 | fan-data-screen |
| notification | 站内消息、接收人、已读状态和投递记录 | fan-auth 中的通用消息能力 |

企业业务档案由 foundation 管理。system 使用企业标识实现账号归属和访问控制。正式建表前还需明确企业、客户、租户是否为同一概念；当前不据此假定多租户模型。

system 管理角色与授权数据；core 中的认证代码负责解析和验证身份。具体业务模块根据身份与授权信息执行企业、部门、本人等数据范围规则。

## 公共技术能力与业务模块的区别

| 目录 | 可以包含 | 边界 |
|---|---|---|
| core | 配置读取、日志配置、通用异常、身份验证技术和身份上下文 | 不放审批实现、企业台账或共享业务 Service |
| db | 引擎、会话、声明式模型基类和通用审计字段 | 不集中存放所有业务模型与业务查询 |
| integrations | 第三方 HTTP 客户端、文件存储、MQTT 与设备协议适配 | 负责协议和格式转换，不决定审批或库存等业务规则 |
| modules | 各领域的接口、规则、模型和查询 | 每个业务对象应有明确的负责模块 |

原来的三个 Socket 服务不对应三个 Python 业务模块。实时连接、订阅和广播属于通信能力；告警、定位和业务事件分别由所属业务模块提供。人员轨迹等数据的归属需要结合实际用途进一步核对，不因使用 WebSocket 就归入通知模块。

设备由多个业务共享时，基础设备档案由 foundation 维护，通行授权和记录归 gate，危险源监测数据归 hazard，具体协议放 integrations。两套门禁协议作为适配实现保留，不直接复制成两套领域模块。

## 模块内部的代码分层

以 foundation 中的岗位管理为例，初期采用以下结构。文件随功能实现创建。

```text
foundation/
  __init__.py
  router.py        HTTP 接口与路由注册
  schemas.py       请求与响应的 Pydantic 模型
  service.py       业务规则、写操作和事务编排
  models.py        SQLAlchemy 数据库表映射
  queries.py       按需要提取的复杂或复用查询
  api.py           出现跨模块调用时提供的稳定入口
```

| 层次 | 应负责 | 不应负责 |
|---|---|---|
| router | 获取校验后的参数和身份，调用业务函数，返回响应 | 拼接 SQL、决定审批状态、提交数据库事务 |
| schemas | 字段类型、必填、长度等输入约束与输出字段 | 执行数据库查询或判断当前用户能否审批 |
| service | 校验业务条件、检查数据范围、组织读写和模块协作 | 依赖 FastAPI Request、返回 HTTP Response |
| models | 表、列、索引、关系及数据库约束 | 获取当前请求、处理 HTTP 异常 |
| queries | 封装复杂查询、联表和查询复用 | 自行提交事务、改变审批状态 |
| api | 向其他模块暴露有限的业务函数和普通数据结构 | 暴露内部 ORM 对象供调用方随意修改 |

简单查询可直接由 service 使用 ORM，暂不强制创建 repository 层、Service 接口、ServiceImpl 或通用 CRUD 基类。Python 函数即可表达的职责先使用函数。

模块变大后按业务子功能拆分，例如 `foundation/positions/` 和 `foundation/equipment/`，各自保留上述职责；不让单个 service.py 无限增长，也不为尚未出现的复杂度预先增加层级。

## 请求与事务

一次新增岗位请求按以下路径处理：

```text
POST /api/v1/foundation/positions
  → router 获取身份、数据库会话与校验后的参数
  → service 检查操作权限、企业范围和岗位名称规则
  → 在同一事务中写入岗位及必要审计记录
  → router 将业务结果转换为响应数据
```

数据库会话的依赖负责创建、异常后的清理和关闭。一个顶层业务用例控制一次写事务，内部函数只执行查询、添加或 flush，不自行 commit。具体采用事务上下文还是显式提交，在数据库骨架实现时统一；不同模块不得各自采用互相冲突的方式。

同库跨模块协作可以共用调用方的会话和事务。网络调用、消息投递或设备操作不能随数据库回滚；重要外部副作用后续采用提交后执行、重试或事务消息记录等方式设计。

## 模块之间如何调用

模块在同一进程中使用明确的 Python 函数协作，无需绕回 HTTP。各模块负责自己的表和写操作，其他模块通过其 api.py 调用。

例如作业票提交审批：work 发起业务操作，调用 workflow 创建审批实例和任务；审批通过后，由 work 校验并修改作业状态。workflow 不导入并直接修改 WorkTicket 模型。

workflow 保存流程实例、节点和审批历史，并通过业务类型、业务标识关联业务记录。审批完成与业务状态变化的协调入口在具体流程落地时实现，保证同一次数据库事务内的一致性。

依赖方向遵循以下原则：

1. core 和 db 不导入业务模块。
2. integrations 的协议适配不导入具体业务实现，由业务用例调用适配器。
3. 业务模块优先调用所属模块公开的业务入口，避免循环导入。
4. 跨模块事务由发起用例协调；出现双向依赖时调整协调位置或接口，不把逻辑搬进 core。
5. dashboard 通过模块提供的统计查询获得数据。确需跨模块 SQL 时单独记录为只读查询，不据此取得源数据的修改权。

初期使用一个 MySQL 数据库和一套 Alembic 迁移历史。模块边界首先通过代码归属与调用规则维护，不要求每个模块建立独立数据库。跨模块外键按数据完整性需求使用，不能让旧数据兼容问题隐含改变数据库约束。

## 权限与安全基础

身份验证、操作权限和数据范围分别处理。路由验证用户身份；业务用例执行授权规则；列表、详情、导出和更新均应用一致的数据范围，不能只在前端隐藏按钮。

密码存储、令牌方案、企业隔离、逻辑删除、审计字段和分页格式在公共能力实现时确定。旧密码与旧登录协议是否兼容，需要显式评估，不因重写而默认继续沿用。

关键业务使用数据库约束与事务保障一致性。例如库存不能只在应用中先读后减，审批也不能只依赖前端避免重复提交；对应业务落地时设计并发控制与幂等规则。

## 目录演进

`app/main.py` 创建应用对象并定义健康接口，`app/__init__.py` 将 `app` 标记为 Python 包。启动方式和环境要求见 [项目 README](../README.md)。

开始实现岗位管理时再创建 `app/modules/foundation/`，接入数据库时再增加会话配置和迁移目录。权限范围、事务回滚、审批状态流转与库存一致性的测试随对应业务加入。

## 学习与实施顺序

1. 建立可运行的 FastAPI 应用、依赖管理、配置与健康接口，理解路由、函数、类型注解和请求响应。
2. 在 foundation 实现岗位管理的最小闭环，学习 Pydantic、ORM、会话、迁移和基础测试。
3. 完善 system 的身份、角色、操作权限和数据范围，将保护应用到岗位接口，再与独立前端联调。前两步仅用于本地学习，不作为可公开部署的业务系统。
4. 选择风险巡检或培训等完整业务，练习事务、模块协作和状态流转；审批能力随真实业务需要提取。
5. 按需求增加任务、文件、设备对接、实时推送、统计和部署能力。

每个阶段完成可运行、可解释的结果后再扩展，不一次生成所有模块的 CRUD。
